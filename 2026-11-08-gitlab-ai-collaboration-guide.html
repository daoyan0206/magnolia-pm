多人 AI 协作 · 精简操作教程

按版本分支协作，不按单项任务创建分支。
命名：version/版本号-日期，例如 version/v0.1.0-20261108。

Windows / PowerShell 示例 · 示例版本号和日期按实际替换 · 更新：2026-11-08

前提：已安装 Git、已获仓库访问与版本分支推送权限。项目基线和启动说明由负责人准备；本教程不执行仓库迁移或远端配置。所有命令在自己的项目目录内按行执行，报错就停。切换分支前先保存并提交本地修改；不要覆盖已有目录、上传密钥或强制推送。

1．主要工作流程是什么？

确定本版范围 → 创建统一版本分支 → 多人 AI 修改并同步 → 整体体验确认 → 合入 main → 冻结交付

每人一份独立项目副本，但共同提交到同一个版本分支。本轮的多项需求放在这个版本中，不为每项需求另外建分支。图为协作示意。

2．仓库地址是什么，如何拉取？

打开 GitLab 项目页面

http://yw-gitlab.miniworldplus.com/miniw/magnolia-product.git

首次下载：每位成员各执行一次

在想存放项目的位置打开 PowerShell：

git clone http://yw-gitlab.miniworldplus.com/miniw/magnolia-product.git
cd magnolia-product

已有正确克隆的人不重复下载。登录按公司认证要求操作；HTTP 地址请在组织允许的可信网络中使用。

3．如何创建并加入统一版本分支？

① 负责人创建：一个版本只创建一次

git switch main
git pull --ff-only origin main
git switch -c version/v0.1.0-20261108
git push -u origin version/v0.1.0-20261108

四行依次是：切到 main → 更新 main → 创建并切到版本分支 → 上传版本分支。

② 其他成员加入：不重复创建远端分支

git fetch origin
git switch --track origin/version/v0.1.0-20261108

如果本地已经有这个分支，改用：

git switch version/v0.1.0-20261108

确认当前分支后，再让 AI 修改：

git branch --show-current

4．多人如何提交？合并规则是什么？

① 修改前：同步版本分支

在版本分支、且没有未提交改动时执行：

git pull --ff-only origin version/v0.1.0-20261108

然后让 AI 修改自己负责的范围，并实际体验。同一个文件或流程先协调，避免同时改。

② 修改后：提交、同步，再推送

git status
git add -- "本次修改的文件路径"
git diff --cached
git commit -m "说明本次调整内容"
git pull --no-rebase --no-edit origin version/v0.1.0-20261108
git push origin version/v0.1.0-20261108

文件路径与提交说明请替换为实际内容。git add 后可列出多个文件；提交前检查不含密钥、运行数据和不相关改动。拉取可能合并别人的新提交，需检查受影响的体验再推送。

发生冲突：停下，请 AI / 负责人说明并协调双方改动，解决后检查、提交，再推送。不要执行强制推送或破坏性回退。推送被拒绝可能是别人刚提交了新内容，先核对并重新同步，不直接覆盖。

③ 整版完成：只发起一次版本合并申请

  1. 负责人通知大家暂停向本版推送，检查最新汇总版本并确认整体体验。
  2. GitLab：Merge requests → New merge request。
  3. Source 来源：version/v0.1.0-20261108。
  4. Target 目标：main。
  5. 写清版本范围，指定产品 / 设计 / 交互确认人。
  6. 冲突解决、体验确认后，由合入负责人点击 Merge。若确认后又有改动，需重新确认。
规则：日常修改直接提交到统一版本分支，不逐项向 main 发 MR；main 由负责人通过版本 MR 合入，不由成员直接推送。合入后不再往旧版本塞新需求，下个版本从最新 main 创建新分支。

5．最终统一到 main 吗？交给开发和测试哪个版本？

是。整体体验确认后的版本分支，通过 MR 合入 main。不是把个人本地内容直接推送覆盖 main。

合入完成后，成员更新本地主线：

git switch main
git pull --ff-only origin main
用途使用版本
日常 AI 修改与阶段体验统一版本分支
最终移交开发、测试main 中本版已确认的固定提交
生成最终 PRD / checklist与移交项目完全相同的固定版本

建议由负责人给本次合入提交打标签：v0.1.0-20261108。在 GitLab 的 Tags → New tag 中填写标签名，指向本次确认的合入提交；入口名称可能随版本变化。交付时附这个标签，不能只说“拿最新 main”。

开发与测试接收的是 main 上的同一冻结版本，不是仍在变化的版本分支。最终 PRD 只包含用户场景与最终规则；checklist 包含前置条件、步骤、预期结果，不包含中途修正或当前验收结果。

一句话：版本分支共同修改，整版确认后合入 main，固定版本交给开发和测试。

本次只更新教程，未创建实际版本分支、执行合并、打标签或推送。项目运行与共享体验环境按仓库真实说明准备；合入 main 不会自动更新运行中的网页。
